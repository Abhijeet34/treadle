# Contributing

Thanks for looking.
This is a small project with one maintainer, so the fastest path to a merged change is a small one that arrives with its test.

## Before you write code

Open an issue for anything larger than a fix.
The design for this project was written before the code, in five audit phases, and a change that contradicts a decision record needs the decision record changed first.
An issue is where that conversation happens, and it is much cheaper than a rejected pull request.

## Setting up

You need Node.js 24.15 or newer.
The `.nvmrc` names the version.

```bash
git clone https://github.com/Abhijeet34/treadle.git
cd treadle
npm ci
npm run check   # tsc --noEmit under strict, then the tests
```

There is no build step for development.
Node runs the TypeScript directly by stripping types, which is why `tsconfig.json` sets `erasableSyntaxOnly` and the code uses `const` objects and union types rather than enums.

## The rules that actually get changes rejected

**Every behaviour change ships with a test that failed before the change and passes after.**
Say so in the pull request, and paste both runs.
A test that has never been red has not been shown to test anything.

**Zero runtime dependencies.**
Development dependencies are fine and are recorded.
A runtime dependency needs a decision record and a conversation first; there is almost certainly a `node:` module or forty lines that covers it.

**The dependency direction is a test, not a convention.**
`src/domain` may import nothing but `src/domain`, and it may not touch the filesystem, the clock, a random source, the process, or the console.
`test/architecture/layering.test.ts` will tell you if you crossed a line.
See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for why.

**Every source file carries `SPDX-License-Identifier: Apache-2.0` near the top.**
`test/architecture/license-header.test.ts` enforces it over every tracked `.ts`, `.js`, `.sh` and `.yml` file.

**A pull request may not remove a test that main already has.**
CI reads the test titles at the merge base and at your branch, and fails on one that main runs and your branch does not.
A test that is renamed, or turned into `.skip`, counts as removed, because a renamed title is a title main had and no longer runs.
This exists because a rebase resolution once took four pre-rebase service files whole, deleted the tests along with the code they covered, and left a green suite over four reverted fixes.
[docs/architecture/adr/0013-a-branch-may-not-remove-a-test-main-has.md](docs/architecture/adr/0013-a-branch-may-not-remove-a-test-main-has.md) argues it.

Check yours before pushing:

```bash
npm run tests-kept          # against origin/main and HEAD
```

If the removal is meant, say so in the commit message with one trailer per test, naming the title exactly as the source declares it:

```text
Removes-test: carries the five components of each row, and the weights that multiplied them
```

One trailer covers one test.
A trailer that names a title nothing in your branch removes fails too, so the declaration cannot be written ahead of the removal or left behind after it.

**No em dashes.**
Use a plain hyphen or a new sentence.

**No machine-detectable origin marks.**
No invisible or zero-width codepoints, no steganographic markers, no "generated by" tags. Provenance a reader uses is welcome; a mark whose job is to let a machine classify the work is not. See [docs/PROVENANCE.md](docs/PROVENANCE.md).

## Commits

Commit messages follow [Conventional Commits 1.0.0](https://www.conventionalcommits.org/).
CI runs commitlint over every commit in a pull request.

```text
feat(domain): add the ready gate evaluator
fix(store): release the lock when an atomic write fails
docs: record the pre-1.0 stability policy
```

Types in use: `feat`, `fix`, `docs`, `chore`, `deps`, `ci`, `test`, `perf`, `refactor`.
The subject is imperative, at most 72 characters, and has no trailing period.
A breaking change carries `!` after the type or a `BREAKING CHANGE:` footer, and [docs/STABILITY.md](docs/STABILITY.md) says what counts as one.

Check yours before pushing:

```bash
npx commitlint --config scripts/commitlint.config.js --from origin/main --to HEAD
```

## Sign off every commit

This project uses the [Developer Certificate of Origin](https://developercertificate.org/).
It is not a copyright assignment.
It is a statement that you wrote the change, or have the right to submit it under Apache-2.0.

```bash
git commit -s -m "fix(domain): refuse a hold expiry in the past"
```

That adds a trailer:

```text
Signed-off-by: Your Name <your.email@example.com>
```

CI checks every commit in a pull request for it and fails on the first one that is missing.
If you forgot, `git rebase --signoff origin/main` fixes the whole branch.

Do not add a `Co-authored-by:` trailer naming a tool or an agent.
Name people.

## Pull requests

One logical change per pull request, small enough for one person to read in one sitting.

The description says the original intent, what changed, how it was tested with the runner's own output, and why the chosen approach is safer than the alternative you rejected.
No marketing, no filler.

CI runs on Linux for a pull request.
macOS and Windows run on a schedule, on manual dispatch, and on the release path, because a three-platform matrix on every pull request spends most of the budget proving what the cheapest runner already proved.
